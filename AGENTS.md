# AGENTS.md — module_gantt

Editable Gantt viewer (React 19 + Vite 8 + TS 6) + **gantt-api** (Fastify + pg, pnpm workspace `server/`). Synthetic construction plan demo; the gantt engine is vendored in `src/components/reui/gantt/`.

## Commands

- **Install**: `pnpm install` — pnpm **workspace** (root app + `server/`); `pnpm-lock.yaml` is the lockfile. Don't use `npm install` (will rewrite lockfile and may break).
- **Dev**: `pnpm dev` → `http://localhost:5173` (proxies `/api` → `127.0.0.1:4600`).
- **Build**: `pnpm build` = `tsc -b && vite build`. Build fails if `tsc` fails; fix type errors before expecting a bundle.
- **Lint**: `pnpm lint` (oxlint only — see `.oxlintrc.json`). No ESLint, no Prettier.
- **Preview**: `pnpm preview` serves `dist/`.
- **No test command** exists; there is no test framework configured. **Round-trip checks** live in `scripts/verify-roundtrip.mts` and run via `pnpm verify` (uses `node --experimental-strip-types`).
- **Server**: `pnpm --filter server dev` (node --watch), `start`, `typecheck` (tsc noEmit), `migrate` (idempotent runner), `seed` (demo plan + hermanas budget/actuals/workforce; el plan siembra `ON CONFLICT DO NOTHING`, las hermanas demo son regenerables y se refrescan incondicionalmente — pisar una edición PUT es aceptado). Backend changes need `systemctl restart gantt-api.service`.

## Path alias

`@/*` → `./src/*` (both `vite.config.ts` and `tsconfig.app.json`). Imports use `@/lib/...`, `@/components/...`.

## Source layout (what lives where)

- `src/main.tsx` + `src/App.tsx` — entrypoint and shell. `App.tsx` fetches the plan bundle (`GET /api/plans/:id` + `/budget` + `/actuals` + `/workforce` + `/calendar` in parallel, decoded at the boundary) with a **demo fallback** (`demo-entity.ts` + `demo-contables.ts` + `demo-workforce.ts` + `demo-calendar.ts`) when the backend is unreachable or a sibling fails its decoder; it keeps the viewer's `ops` and derives `livePlan = applyOps(basePlan, ops)` for the EVM panel. Online it also keeps the CR queue (`GET /api/plans/:id/change-requests`, refetch after propose/decision), passes `onProposeChangeRequest` down to the changeset zone **solo cuando la sesión es editor+** and renders `ChangeRequestsPanel` with `canDecide`; after an apply (or a decision 409) it bumps `reloadKey` so the bundle refetches and the viewer REMOUNTS via `key={planId:revision}` (its internal events state doesn't re-init from props alone — existing limitation). Session state (`me`, `authOpen`, `canWrite`, `canDecide`, `onWriteRejected`: un 401 en cualquier escritura abre el login) y el panel `TimesheetsPanel` viven aquí. Offline: CRs/propose hidden, workforce/calendar fall back to the demo builders. `?stress=N` (dev benchmark) swaps the whole bundle for `buildStressEntity(N)` — never fetches, never persists; `useStressBenchmarks` logs mount paint + scroll frame budget to the console (documented in `scripts/gen-stress-plan.mts`).
- `src/components/gantt-plan/` — app-level viewer (`GanttPlanViewer.tsx` is the **umeJSON black box**; optional `workforce` prop adds the «Cuadrilla» tree column and the «Sobrecarga» heatmap column), the changes JSON panel (`ChangesetPanel.tsx`, with the propose button when online AND the session can write), the CR queue (`ChangeRequestsPanel.tsx`, patrón `EvmPanel`: badges de estado, impacto congelado, Aprobar/Rechazar/Aplicar, gated por `canDecide`), the EVM cards (`EvmPanel.tsx`), the tree-columns show/hide dropdown (`TreeColumnsMenu.tsx`), **PlanFiltersMenu** (filtros del árbol: texto/responsable/fase/crítica/drift/hitos; el matching vive en el viewer, el menú es presentacional) y **AuthPanel/TimesheetsPanel** (login + parte de horas). This is where to add app features.
- `src/components/reui/gantt/` — **vendored gantt engine** (NOT an npm dep). Edit `gantt.tsx` (main) and siblings here when extending the engine. New generic props for the tree panel live around `gantt.tsx:1215`. Tree columns resize from their header edge handles (drag/±16 arrows/double-click reset; incl. the pinned name column via the reserved id `GANTT_NAME_COLUMN_ID`) — widths flow through `columnWidths` state and a `--gantt-cw-*` CSS var on the tree content root, so the live drag never re-renders rows. **Row virtualization** lives in `gantt-view.tsx`: ONE offsets memo (`rowGeometry`: tops/heights acumulados en rem desde rows+rowBars) alimenta tree rows, timeline rows, los spacers y la capa de dependencias; la ventana visible (+10 overscan) se mide del scroller del timeline con rAF-throttle + ResizeObserver y se CLAMPA en useLayoutEffect pre-paint. Dos invariantes duros: la ventana INICIAL nace chica (`INITIAL_WINDOW_ROWS = 80` — React materializa lo que el primer render pide ANTES del clamp; «arrancar ancho» congeló el tab con 20k filas) y `GanttDependencyLayer` recibe offsets+ventana y DROPEA conectores cuyo extremo cae fuera de la ventana (el retarget a ancestro es SOLO para filas colapsadas). El reorder por grip mapea límites del slice visible a índices globales vía `rowWindowRef`. **Milestones** (`GanttEvent.milestone`, duration 0): the ONLY legal zero-width segment — rendered as a square hit-box of `laneHeightRem` centered on the instant, the paint is a `rotate-45` diamond inside (`gantt-bar.tsx`, bitono: resting tint → strong progress tint at 100%; critical stroke and dirty tint keep applying); `canResize` vetoes them, the label always rides outside, the tooltip drops end/duration rows, the drag ghost is the same square footprint. Inline title editing: `treePanel.titleEditable` + settings callback `onResourceTitleCommit` → `EditableTreeTitle` (doble clic/F2, Enter/blur commit, Esc cancela, blank nunca confirma; solo sobre la etiqueta DEFAULT).
- `src/components/reui/gantt/gantt-color.ts` — concrete-color helpers for the bar paint model. **All phase colors must be concrete hexes**; `var()` chains fail silently in some browsers (the whole chain goes invalid and paints transparent). Exports `baselineTones(color, stack)` for baseline marks (pastel ramp by depth) and `barTones(color)` for live bars (80% pastel + phase at α 0.85). Also `DIRTY_TINT = "#fecaca"` (red-200) for the modified/drifted state — gray-200 was retired: it sat at the same OKLCH lightness as every resting pastel (L≈93, chroma ≈0) and was invisible next to them.
- `src/components/ui/` — shadcn-style primitives. `slider.tsx` is **custom** (no native `<input type="range">`); it has its own pointer/keyboard handlers.
- `src/data/plan-departamento.ts` — synthetic plan regenerated on every mount, anchored to the current week (see `:57`). WBS schema v2. Phase `color` is a concrete hex (Tailwind 500-level) so every paint path (live bars, baseline tones, swatches) renders without runtime CSS-variable resolution. A few events ship with seeded `baselines` so the bitácora has content on load (panel); they keep that history untouched. `acta-entrega` ships as a **milestone** (`kind: "milestone"`, duration 0) — the diamond in the demo. Re-exports types from `@/lib/plan-types` for compat.
- `src/lib/plan-types.ts` — shared types: `PlanJSON` (+`statusDate?`, +`schedulingOptions?: { outOfSequence: "retainedLogic" | "progressOverride" }`), `PlanEvent` (+`baselines?`, +`kind?: "task" | "milestone"` — absent = task, the canonical form, +`priority?: number` 1..1000 para nivelación, ausente = 500), `PlanBaseline`, `PlanResource` (+`responsable?`), `PlanPhase`, `EventData` (+`initialStart?`/`initialEnd?`, +`baselines?`). Todos los campos nuevos son ADITIVO-OPCIONALES (schema sigue v2); `data/` imports types from here, never the other way. The bitácora de líneas base lives in `EventData.baselines` (append-only snapshots; only real captures populate it — see `plan-mapper.ts`); `initialStart/End` are the hidden "modified vs original" anchor — not visible as a bitácora entry until the first capture on a drifted bare task materializes them as LB1.
- `src/lib/plan-mapper.ts` — `PlanJSON` → `GanttEvent[] + GanttResource[]`. Pure on the plan received: phase colors come from `plan.phases`, status is derived from the event's own `progress`, `responsable` comes from `resource.responsable`, `kind === "milestone"` maps to the engine's `milestone: true`. Recursive tree builder, preserves sibling order, treats orphans/cycles as roots. **No synthetic LB1**: baselines exist only where a real capture happened (the seeded demo history, or an explicit *Fijar línea base*); events without history carry none. A load-time LB1 used to anchor every bar's original dates, so each drag left a full-size colored remnant pinned at the old spot — removed. Instead the mapper stamps `initialStart/initialEnd` into `EventData` so drift on a bare task measures against the plan's original dates without polluting the bitácora. First explicit capture on a *drifted* bare task materializes LB1 from those initial dates and appends the capture as LB2; a clean bar captures nothing (see *Fijar línea base en cascada* below).
- `src/lib/umejson/schedule.ts` — pure dependency graph helpers. **`dependentClosure(deps, seedIds)`** returns the transitive successors reachable from `seedIds` along `fromEventId → toEventId` (BFS, visited set, seeds excluded). Used by *Fijar línea base* to fan out captures across dirty dependents. **`wouldCreateCycle`** is the edit-time veto on `from → to`. **`cascadeSchedule`** is the forward-only forward pass that emits per-edge documented adjustments (see `ChangesetPanel` for the codec surface). **`snapToDependency(plan, dep)`** seats a successor EXACTLY at its constraint's bound (FS→pred end, SS→starts, FF/SF→ends; lag applied, duration preserved) — bidirectional BY DESIGN: it's the edge-shape-edit gesture (`updateDependency` en el recorder), distinto de la cascada que sigue siendo forward-only. **`impliedLagDays(dep, pred, succ)`** es su contraparte de lectura (lag implícito en fechas vivas; el DependencyPanel lo muestra para que un drag se refleje al soltar). `DependencyCause.shiftDays` es firmado (negativo = reasiento hacia atrás). **Convenciones statusDate**: la cascada lee `plan.statusDate` + `plan.schedulingOptions.outOfSequence` del PROPIO plan — frozen actuals (progreso > 0 iniciados antes del corte nunca se mueven), retainedLogic (default: asiento desde el fin vivo) y progressOverride (asiento pisando el corte con duración restante `(100−progress)/100`); sin statusDate el comportamiento es el clásico byte-idéntico.
- `src/lib/umejson/baselines.ts` — **política de drift promovida** (runtime-pura): `vigenteBaseline` (máxima versión, no última posición), `driftReference`/`isDrifted` sobre tipos del plan (ISO strings; se comparan **instantes**, no strings — `…Z` y `…T00:00:00.000Z` son el mismo momento), `driftDays` (mismo redondeo que el panel de bitácora) y `restoreBaselineOp` (reversión a una versión capturada como `UpdateOp` — la bitácora es read-only, restaurar ES una edición). El viewer adapta `GanttEvent`→`DriftSubject` en su único punto de traducción (`isDriftedEvent`); no existe otra copia de la regla.
- `src/lib/umejson/change-request.ts` — contrato del módulo de control de cambios (runtime-puro): entidad propia **`GanttChangeRequest`** (el schema del plan queda congelado en v2), `ChangeRequestPayload` anclado al plan (`planEntityId` + `planAnchor` + **`planRevision`** — el binding que protege de verdad: `planAnchor` es una fecha que `applyOps` preserva intacto, así que ediciones intermedias se le escapan; la revisión no — apply contra otra revisión es 409 y la CR hay que re-proponerla), `buildImpactSnapshot(basePlan, ops, budget?)` (afectados = ops + `dependentClosure` sobre el grafo post-ops; Δ congelado al proponer contra vigente baseline ?? fechas del plan base; eventos creados no llevan referencia; con budget adjunta **`costImpact`** — modelo labor-burn: `dailyLaborBurn = breakdown.labor / duraciónDíasReferencia`, `projectedExtraCost = Σ driftDays × burn` con signo [negativo = ahorro], `extendedDays = Σ driftDays > 0`; sin budget no hay costImpact, sin desglose el burn es 0), `createChangeRequest` (el snapshot nace del MISMO plan al que se ancla), `buildChangeRequestEntity` (envelope nuevo, `crypto.randomUUID()`, relation → plan), transiciones legales `proposed → approved | rejected`, `approved → applied` (terminal; `transitionChangeRequest` devuelve null en ilegales), y `encodeChangeRequest`/`decodeChangeRequest` con la misma disciplina sentinel/statusLog que `encodeUpdatedPlan`. El `statusLog` del payload acepta timestamps SENTINEL (propuesta pre-persist); el `lifecycle` del envelope no. Actores (`requestedBy`/`decidedBy`) reservados vía SENTINEL; el backend los estampa con la identidad de la sesión (`req.actor.name`, fallback `DEFAULT_ACTOR`).
- `src/lib/umejson/leveling.ts` — **nivelación runtime-pura**: `crewDemand` (curva cuadrilla→día UTC→headcount; un evento ocupa SOLO los días laborables de su calendario en `[start, end)` con el MISMO redondeo de día entero que el resto del árbol; hitos ocupan nada), `overallocations` (corridas contiguas `{ crewId, from, to, peak, excessPersonDays }`), `eventOverloadDays` (heatmap de la columna «Sobrecarga») y `levelPlan(plan, workforce, { resolve?, maxIterations? })`: delay-based sin splitting, víctimas por corrida ordenadas (prioridad ↓, holgura total ↑, inicio ↑), asiento en el primer laborable posterior conservando duración + hora del día. **Regla anti-freeze: cada tarea se nivela UNA sola vez por pasada (`leveledOnce`)** — sin ella una cadena que re-crea la sobrecarga re-nivelaba el mismo evento deslizando el proyecto décadas y encareciendo cada CPM hasta colgar el hilo minutos. Hitos jamás son víctimas; demanda propia > capacidad → la corrida se estaciona como sin resolver (mover no arregla). Salida: `UpdateOp[]` puros de fechas (víctimas sin cause; dependientes con causa de cascada documentada) + reporte. El viewer los aplica vía `recorder.recordOps()` y espeja fechas con `applyAdjustmentsTo` (que acepta moves planos `{eventId,start,end}`).
- `src/lib/umejson/timesheet.ts` — hermana **`GanttTimesheet` v1** (parte de horas): un doc por (actor, semana) — `weekOf` + `entries[{ id, actor, date, eventId, hours ∈ (0,24], note?, status }]`; transiciones `draft → submitted → approved | rejected` via `transitionEntry` (aprobado terminal, ilegal = null, disciplina CR). `decodeTimesheet(input, plan?, _planEntityId?, workforce?)` valida refs contra el plan y la tarifa de la cuadrilla asignada; el ESTADO umeJSON del envelope es siempre "active" — los estados del parte viven en cada entry.
- **Fijar línea base en cascada** (`GanttPlanViewer.captureBaseline`): only bars that are *drifted* (their live dates differ from their drift reference — vigente baseline, else the mapper-stamped original dates; see `driftReference` in `umejson/baselines.ts`) capture. The seed follows the same rule as its transitive dependents along the dependency graph: a clean bar gets no entry, because snapshotting an unmoved bar would append an entry identical to its reference — a duplicate whose only effect was a ghost twin painted under the live bar. **First capture on a drifted bare task materializes LB1 lazily**: version 1 at `initialStart/initialEnd` with `capturedAt = plan.anchor` and reason `baselineOriginalReason` ("Carga inicial del plan"), then the capture as LB2 — the two-entry log the old load-time LB1 used to give, without painting ghosts on unmoved bars. Seed reason `baselineManualReason`; drifted dependents capture with reason `baselineCascadeReason(seedTitle)`. All capture entries share a single `capturedAt`. Persisted state only: «Reiniciar plan» wipes everything as before; ChangeOps are not touched.
- **Baseline ghosts are off.** `getEventBaselines` (viewer) is permanently empty — the ambient timeline never paints baseline marks. The newest bitácora entry is the drift REFERENCE — its presence is signaled by the dirty tint, never by an ambient ghost: painting it by default stamped a twin under the live bar at capture time that only "revealed" itself after the bar moved. The bitácora panel and the hover-time reprojection (`eventBarOverlays`) read `data.baselines` directly and work without the marks.
- `src/lib/umejson/schema.ts` — `UmeJsonEntity` type + `decodeUmePlan()` hand-rolled validator (envelope + payload; validates the `kind` enum `"task" | "milestone"` when present, `priority` entero 1..1000 cuando presente, `statusDate` ISO y `schedulingOptions.outOfSequence` enum — todo aditivo-opcional). Exports `SENTINEL = "RESERVED_FOR_SYSTEM"`, `ENTITY_NAME = "GanttPlan"` and `validateUmeEnvelope()` (shared envelope checks for the sibling entity decoders).
- `src/lib/umejson/cpm.ts` — **CPM runtime-puro**: `cpmSchedule(plan)` computa forward pass (ES/EF, reusando `earliestStart` + orden Kahn de `schedule.ts`), backward pass (LS/LF desde el fin del proyecto = max EF), holgura total (LS−ES, días laborables propios, mismo redondeo que la bitácora), **holgura libre** (`freeFloatDays`: cuánto puede deslizarse cada evento sin empujar a nadie — min sobre salientes de la fecha tardía que cada tipo restringe − lag − EF; sin sucesores, fin del proyecto; clamp 0) y conjunto crítico (float total 0). Convención **as-planned**: ES = max(inicio planificado, restricciones) — la holgura que el planificador "guardó" arrancando tarde NO es float. Con `plan.statusDate` + `outOfSequence: "progressOverride"`, el trabajo NO iniciado tiene piso ES = statusDate (los congelados — progreso > 0 iniciados antes del corte — mantienen su instante). Una tarea aislada es su propia ruta crítica. El viewer señaliza barras críticas con un **trazo `inset-ring` en el color de fase** vía `getEventBarClassName`; NUNCA con el relleno — el invariante bitono es **reposo siempre claro, full-strength reservado al overlay de avance**, para que una crítica al 0% no se lea como avance.
- `src/lib/umejson/budget.ts` — entidad hermana **`GanttBudget`** (BAC por evento, moneda, time-phasing `uniform`, `relations[] → plan`): tipos, `buildBudgetEntity` y `decodeBudget(input, plan?, planEntityId?)` con el mismo DSL de schema (BAC ≥ 0 finito, refs contra el plan suministrado, relación exactamente 1 → GanttPlan). El payload v1 ganó **`breakdownByEvent?`**: partición `labor/material/equipment` por evento que debe sumar EXACTO al `bacByEvent[eventId]` (igualdad exacta, partes ≥ 0 finitas); opcional/aditivo, `schemaVersion` sigue en 1.
- `src/lib/umejson/workforce.ts` — entidad hermana **`GanttWorkforce`** v1 (RRHH de obra): `crews: [{ id, title, specialty, headcount, dayRate }]` + `assignmentByEvent: Record<eventId, { crewId, headcount }>]`, `relations[0] → GanttPlan` (exactamente 1). Decoder con `validateUmeEnvelope` + refs cruzadas (crew inexistente, evento desconocido vs plan, headcount ≥ 1, dayRate ≥ 0 finito) + `buildWorkforceEntity`.
- `src/lib/umejson/actuals.ts` — entidad hermana **`GanttActuals`** (AC acumulado por evento + `dataDate` de corte + `planAnchor`): `decodeActuals` valida el corte ISO, AC ≥ 0, refs contra el plan y el cross-check de `baselineVersionByEvent` contra la bitácora real (la versión anclada debe existir).
- `src/lib/umejson/evm.ts` — **EVM runtime-pura**: `computeEvm(plan, budget, actuals)` produce PV (time-phasing uniforme del BAC sobre la ventana de referencia de drift — baseline vigente/anclada, si no las fechas del evento, clamped [0, BAC]), EV (BAC × progress), AC (corte) y SV/CV/SPI/CPI/EAC/ETC/TCPI/VAC por evento y proyecto. Índices null cuando el denominador carece de sentido (PV 0, AC 0, CPI 0 → EAC); CPI 0 con AC > 0 es una respuesta real, no null. Nada se persiste — EVM es una lente. `pvFraction` exportada para tests. El corte resuelve `actuals.dataDate ?? plan.statusDate ?? now` (orden documentado; un corte vacío jamás NaN-ea las métricas).
- `src/data/demo-entity.ts` — `buildDemoEntity()` + `DEMO_PLAN_ID`: el envelope demo compartido por el fallback de App y el seed del backend (una sola definición).
- `src/data/demo-contables.ts` — builders demo de `GanttBudget`/`GanttActuals` sobre un plan dado (tarifa por fase × días para BAC, con desglose labor/material/equipo que suma EXACTO al BAC — labor 45–60% según fase, enteros, equipo absorbe el redondeo; un hito [`kind: "milestone"`] reserva BAC 0 con partición 0/0/0, sin piso de 1 día; BAC × avance × wiggle determinista [0.85–1.15] para AC; ancla de baseline vigente donde hay bitácora). Mismo patrón que las baselines sembradas: sintético pero realista.
- `src/data/demo-workforce.ts` — builder demo de `GanttWorkforce`: las ~14 cuadrillas derivan de `RESPONSABLES` (única fuente: `plan-departamento.ts`), cada una con especialidad y tarifa/día/persona realista (peón ≈ 850, albañil ≈ 950, eléctrico ≈ 1 100, residencia ≈ 1 500 MXN); `assignmentByEvent` = evento → cuadrilla del `responsable` de su recurso (demo 1:1). Determinista (hashes sobre ids). **Sobrecarga sembrada**: tras asignar, el headcount de la cuadrilla con más eventos se recorta por debajo de su pico real de demanda concurrente (solo si pico ≥ 4) para que «Sobrecarga»/«Nivelar recursos» tengan material visible sin tocar schema v1.
- `src/data/stress-plan.ts` — generador determinista (`buildStressPlan(n)` / `buildStressEntity(n)`): WBS raíz→fases→tareas (10 por fase), UNA cadena FS global (hitos cada 25 eventos incluidos en la cadena), prioridades/duraciones/progresos por hash de id, fechas via `addWorkingDays` sobre un calendario Lun–Vie inline. Compartido por App (`?stress=N`, nunca fetchea ni persiste) y por el CLI `scripts/gen-stress-plan.mts` (que además valida contra el decoder real antes de reportar).
- `server/` — **gantt-api** (paquete del workspace): Fastify + pg escuchando SOLO en `127.0.0.1:4600` (nginx proxyea `/api/` mismo origen). `src/db/migrations/*.sql` + runner idempotente (`migrate.ts`; 001 entities · 002 sibling index · **003_actors** — directorio de identidad); `entities.ts` (store híbrido: documento íntegro en JSONB + columnas promovidas `status`/`revision`/`plan_entity_id` mantenidas por el servidor, lock optimista vía `revision`; `PutEntityArgs.status` overridea la columna promovida para CRs — `payload.status`, no `state.current`, que el índice `ume_cr_queue` filtra por `status='proposed'`; `stampChangeRequestSentinels` además del envelope estampa el `statusLog` del payload CR y los actores; `seedOverwrite` = refresh incondicional de hermanas demo); `index.ts` (health + GET/PUT `/api/plans/:id` y `/api/plans/:planId/budget|actuals|workforce|calendar` vía `registerEntity`, con gate de rol en cada PUT; endpoints CR propios — NO via `registerEntity`, semántica distinta: cola `created_at DESC`, propuesta con `requireRole("editor")`, decisión con `requireRole("aprobador")`, apply con binding de revisión → 409 y escritura plan+CR en UNA transacción); `auth.ts` (sesiones: cookie HMAC `gantt_session` HttpOnly/SameSite=Lax/12 h firmada con `SESSION_SECRET`, preHandler global que resuelve `request.actor`, ladder `visor < editor < aprobador` via `requireRole(req, reply, min)` — 401 sin sesión / 403 con rol insuficiente; passcode compartido `ACTOR_PASSCODE`, timingSafeEqual); `timesheets.ts` (endpoints propios: GET cola con filtros, PUT REPLACE de la semana del actor autenticado — solo entradas propias draft/submitted, id determinista sha256(planId|actor|weekOf) — y `POST /api/timesheets/:entryId/decision` aprobador; al aprobar, merge a `GanttActuals` EN LA MISMA transacción con retry interno ante carrera aprobación×aprobación: AC = Σ horas aprobadas × dayRate/8, REPLACE total). Importa los módulos de `src/lib/umejson/` **verbatim** — única fuente de verdad del contrato. Node ≥ 22.18 corre el TS nativo (strip-types), sin transpilador.
- `src/lib/umejson/codec.ts` — anti-corruption layer: `ChangeOp` union (UpdateOp/CreateOp/DeleteOp/AddDependencyOp/UpdateDependencyOp/RemoveDependencyOp/**UpdateResourceOp/UpdatePlanSettingsOp**), pure `applyOps(plan, ops)`, `encodeUpdatedPlan(base, plan, opCount)`. The recorder re-exports `ChangeOp` from here. `UpdateOp.patch` carries an optional `kind?: "task" | "milestone"`: applying `"milestone"` stamps the field, applying `"task"` DROPS it (destructure-drop, same canonical-form criterion as `dependencies`) so a toggle ida y vuelta round-tripea byte-idéntico; dates-only ops never synthesize `kind`. También `progress?: number` (avance físico 0..100, aditivo igual que kind — ausente = no toca; el % nunca mueve fechas). `UpdateResourceOp` (`res:<id>` en el fold del recorder) reconstruye `resources` LAZY: sin ops de recurso el array nunca se toca (round-trip byte-idéntico), id desconocido ni siquiera lo re-mapea. `UpdatePlanSettingsOp` hace fold por CAMPO con drop canónico: `statusDate/schedulingOptions === null` DROPEA el campo, objeto lo reemplaza wholesale.
- **Edición inline y duración por teclado**: `updateResourceTitle(resourceId, title)` rechaza blank y graba `UpdateResourceOp` (el viewer deriva `resources` del plan VIVO, así rename+undo se reflejan solos); `setEventDuration(eventId, n)` re-asienta el FIN via `addWorkingDays` sobre el calendario DEL evento (hitos vetados, n ≥ 1 entero) y QUEUA la cascada como el drag (`consumePendingCascade`). `recordOps(ops)` incorpora ops ya computados (salida de kernels como la nivelación) con la misma disciplina fold-by-key + historial; targets desconocidos se descartan.
- **Deshacer/Rehacer** (`changeset.ts` + viewer): el recorder mantiene snapshots del ARRAY de ops (`history`/`future`, tope 50) porque el fold-by-key hace imposible deshacer op a op; toda mutación pushuea el snapshot previo en `notify()` y limpia `future`. `undo()/redo()` devuelven los ops vigentes; botones junto a «Reiniciar plan» + atajos `Ctrl+Z`/`Ctrl+Shift+Z` (inertes en inputs). El viewer reconstruye `events = toGanttEvents(livePlan)` post-undo. **Limitación aceptada**: las capturas de bitácora de la sesión viven en el estado del engine — un undo posterior las descarta (misma semántica de wipe que Reiniciar). Documentado en README y en `handleUndo`.
- **Registrar avance** (`ProgressPanel` en el viewer): menú contextual → % viaja como `setEventProgress` (op auditable, mergeada con drag/kind vía `mergePatchExtras`); AC opcional va a `onCaptureActuals` de App con dataDate nuevo — online hace PUT de la hermana actuals con `expectedRevision` leída del header **`x-ume-revision`** que el GET añade a toda entidad, offline queda en memoria para el EVM. AC es acumulado: semántica REPLACE por evento.
- `src/lib/changeset.ts` — `ChangesetRecorder` accepts a `createDraft(slot)` opt; the draft is the host module's responsibility (the recorder doesn't know the domain). `onEventUpdate` allows `end === start` ONLY for milestones (the gesture preserves duration 0) and MERGES a previously recorded `kind`/`progress` into later ops (`mergePatchExtras`: drag/cascada/snap tras una conversión o un avance nunca pierden lo grabado). `setEventKind(eventId, kind)` records the toggle: → milestone collapses `start = end = fin actual` (FS dependents stay bound); → task keeps the instant as start and restores the duration from the base plan when it knew the event as a task (else 1 day) — duración contada en LABORABLES del evento cuando hay calendario; both directions run the dependency cascade and queue it via `pendingCascade` for the host to merge.
- **Tarea ⇄ hito** (`GanttPlanViewer.handleToggleMilestone`, menú contextual sobre la barra, debajo de «Historial de líneas base»): hito de finalización con duración 0. Todo viaja como `UpdateOp` con `patch.kind` (auditable, reversible con «Reiniciar plan»); el viewer espeja el resultado + cascada en un solo `setEvents`. Crear hitos desde cero queda fuera del alcance.
- **Dependencias**: crear SOLO por arrastre desde los connect handles de la barra (`onEventConnect` → `recorder.addDependency`, veto de ciclo en `canConnectEvents`); el menú contextual NO ofrece alta — solo «Quitar dependencia» (y el clic en el conector abre `DependencyPanel` con la misma acción).

## Bar paint model (bitono)

Live bars are painted in two layers; both tones come from the consumer through `GanttViewConfig`:

- **Resting surface** (`--gantt-bar-tint`): soft pastel, concrete hex. Defaults to `var(--gantt-event-color) / 20` (translucent) when no tone is supplied; switches to opaque (`data-bar-tinted` attribute, driven by `colorOverride` OR `progressTintOverride`) when any tone is provided. Hover/selected darken via `bg-black/5` on the opaque layer.
- **Progress overlay** (`--gantt-progress-tint`): full-strength phase color at α 0.85. Border at α 0.65. Defaults to `var(--gantt-event-color)`; switched by `progressTintOverride`. The two layers can move independently — a consumer paints a bitono.

Consumer entry points on `GanttViewConfig`:

- `getEventBarTone({ event }) => { resting?, progress? } | undefined` — per-event bitono. The `GanttPlanViewer` uses this to derive the resting fill from `barTones(ev.color)` and to mark the bar DIRTY (resting = `DIRTY_TINT`, red-200) when `ev.start/end` differ from its drift reference (vigente baseline = highest-version `data.baselines` entry, else the mapper-stamped `initialStart/initialEnd`). Drag-release and *Fijar línea base* both flow through `events`, so the dirty bit updates without an effect. Callback identity MUST be stable (wrap in `useCallback` over the derived `Map<eventId, tone>`).
- `getEventBarClassName({ event }) => string | undefined` — per-event extra classes on the live bar (merged after the engine's own). The channel for STATE chrome that must not borrow the fills (the critical-path `inset-ring-1 inset-ring-(--gantt-event-color)` stroke). Same memoize contract as `getEventBarTone`.
- `getSummaryBarTone({ resource, events }) => { resting?, progress? } | undefined` — same contract for parent rollups. Used so the inline summary bar matches the live-bar bitono.
- `eventBarOverlays[eventId].progressColor?: string` — companion to `color` for history-version previews: `color = baselineTones(...).fill` (pastel), `progressColor = baselineTones(...).full` (strong), so hovering a bitácora entry shows the version's bitono on the bar itself.

Vendored engine additions: `GanttBar` exposes `progressTintOverride`; both overrides feed CSS vars and turn on `data-bar-tinted` so the resting fill switches to opaque.

## Conventions (differ from defaults)

- **Styling**: Tailwind v4 with `@theme inline` and `data-[slot=…]` / `data-[state=…]` variants. No CSS modules.
- **Types**: `any` is forbidden unless marked with an explicit eslint-disable and a comment explaining the adapter.
- **Comments**: only where intent isn't obvious.
- **WBS depth is color, not indent.** Titles are left-aligned at the gutter; depth shows as row background via `wbsLevelStyle(depth)`. The depth slider (`WbsLevelSlider` in `gantt-plan/`) controls `collapsedGroups`: groups with `depth >= level` collapse. Default level = `maxDepth` (all expanded).
- **Concrete-hex colors only.** Phase colors flow through `barTones()` and `baselineTones()` → CSS background, and the derivation chain uses `canvas.getContext("2d").fillStyle` for runtime resolution. CSS variables in `var()` chains are tolerated by the helpers but unreliable in the wild; pin hexes in `data/plan-departamento.ts` to keep paint predictable.
- **PlanJSON v2 quirks** (`plan-departamento.ts`):
  - `parentId` is free — can point to any resource, not just a phase.
  - `phaseId` is **inheritable**: missing `phaseId` falls back to the nearest ancestor's (bar color comes from the resolved chain).
  - `PlanPhase` is only color metadata (`id`, `title`, `color`) — no `resourceIds`.

## Verification order

Run after changes:

```
pnpm lint && pnpm build && pnpm verify
```

(`tsc -b` runs inside `build`, so type errors surface there. Lint is fast; run first. `pnpm verify` round-trips the umeJSON codec via `node --experimental-strip-types`.)

Backend changes add:

```
pnpm --filter server typecheck && pnpm --filter server migrate
curl -s localhost:4600/api/health   # smoke (db must be true)
```

## Deploy

`https://gantt.aeon-ia.com/` is the live demo for this project. **Every change set ships to it** — verification passing is not enough, the user is on this subdomain. Treat the next command as a fourth step of the workflow above; do NOT finish a task without running it.

```
pnpm build && rsync -a --delete dist/ /var/www/apps/gantt/
```

- `pnpm build` regenerates `dist/` with a new content-hashed bundle name; the rsync below only overwrites what exists.
- `--delete` is mandatory — stale hashed assets linger otherwise and nginx happily serves them.
- After the rsync, confirm the deployment took: `curl -s https://gantt.aeon-ia.com/ | grep -oE 'assets/index-[A-Za-z0-9_-]+\.js'` should match the hash printed by `pnpm build`. If it doesn't, the rsync didn't land.
- If the user reports "no veo cambios", they are almost certainly hitting a cached `index.html` (assets are hash-busted and update on their own). Suggest a hard reload (Ctrl+Shift+R / Cmd+Shift+R) and re-check the served bundle hash against `ls dist/assets/`. The vhost pins `location = /index.html { add_header Cache-Control "no-cache"; }` so the document always revalidates (ETag 304s) while hash-busted assets stay cacheable — do NOT remove that header: without it heuristic caching serves a stale document referencing an old bundle after a deploy.
- **Backend**: the API runs as the systemd unit `gantt-api.service` (user `gantt`, `EnvironmentFile=server/.env`, `ExecStart=node server/src/index.ts`). Code changes need `systemctl restart gantt-api.service`; nginx proxies `/api/` → `127.0.0.1:4600` from the TLS vhost (same origin, no CORS) with `limit_req` 10r/s burst 20 (zone `gantt_api` defined in `/etc/nginx/conf.d/gantt-api-limit.conf`). Credentials live ONLY in `server/.env` (gitignored, mode 640 root:gantt) — never in tracked files.

## Gotchas

- The gantt engine is **vendored**, not installed from npm. There's no `@reui/gantt` in `package.json` — don't add it; extend `src/components/reui/gantt/` directly.
- The repo is a **pnpm workspace** (`pnpm-workspace.yaml` → `server`); install at the root installs both packages.
- `src/lib/umejson/` is **runtime-pure**: no value imports with the `@/` alias (the path alias is resolved by Vite/tsc, not by Node). Imports between modules in that tree use relative paths with explicit `.ts` extensions (`from "./schema.ts"`) so the same files can be loaded by `pnpm verify` under `node --experimental-strip-types` AND by `tsc -b`/`vite build` AND by `server/src/index.ts` (Node ≥ 22.18 strip-types, no transpiler).
- `server/tsconfig.json` uses `moduleResolution: bundler` (typecheck-only, noEmit) so the frontend tree's `@/` alias imports resolve; at runtime only `.ts`-suffixed relative imports are ever executed.
- `tsconfig.app.json` has `noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly`, `verbatimModuleSyntax: true`. Watch for unused imports and enum-style code.
- README's "Scripts" section says `npm install` — **the lockfile says pnpm**. Use pnpm.
- **Perf invariants** (both froze the live tab once — don't regress them): the row window starts at `INITIAL_WINDOW_ROWS = 80`, never "wide then clamp" (React materializes what the first render asks for, pre-paint clamp or not); and leveling marks each task `leveledOnce` — re-victimizing tasks on constraint chains slides the project decades and makes every later CPM pass slower until the tab hangs.
- **Roles are a server-side gate only**: the frontend hides propose/decide buttons via `canWrite`/`canDecide`, but never trust it — every write route answers 401/403 through `requireRole`. The login passcode is shared (`ACTOR_PASSCODE`); roles come from the actor row, not credentials.
- **Timesheets approval REPLACES the demo AC**: approving any entry recomputes `GanttActuals.acByEvent` as Σ approved hours × crew dayRate / 8 across ALL weeks (seeded demo actuals are overwritten — documented REPLACE semantics; re-seed restores them).
- Benchmark pages (`?stress=N`) build the bundle in memory and never persist; they exist to measure virtualization (console marks), not as a feature.
