# AGENTS.md — module_gantt

Editable Gantt viewer (React 19 + Vite 8 + TS 6) + **gantt-api** (Fastify + pg, pnpm workspace `server/`). Synthetic construction plan demo; the gantt engine is vendored in `src/components/reui/gantt/`.

## Commands

- **Install**: `pnpm install` — pnpm **workspace** (root app + `server/`); `pnpm-lock.yaml` is the lockfile. Don't use `npm install` (will rewrite lockfile and may break).
- **Dev**: `pnpm dev` → `http://localhost:5173` (proxies `/api` → `127.0.0.1:4600`).
- **Build**: `pnpm build` = `tsc -b && vite build`. Build fails if `tsc` fails; fix type errors before expecting a bundle.
- **Lint**: `pnpm lint` (oxlint only — see `.oxlintrc.json`). No ESLint, no Prettier.
- **Preview**: `pnpm preview` serves `dist/`.
- **No test command** exists; there is no test framework configured. **Round-trip checks** live in `scripts/verify-roundtrip.mts` and run via `pnpm verify` (uses `node --experimental-strip-types`).
- **Server**: `pnpm --filter server dev` (node --watch), `start`, `typecheck` (tsc noEmit), `migrate` (idempotent runner), `seed` (demo plan + hermanas budget/actuals/workforce; el plan siembra `ON CONFLICT DO NOTHING`, las hermanas demo son regenerables y se refrescan incondicionalmente — pisar una edición PUT es aceptado). Backend changes need `systemctl restart gantt-api.service`.

## Path alias

`@/*` → `./src/*` (both `vite.config.ts` and `tsconfig.app.json`). Imports use `@/lib/...`, `@/components/...`.

## Source layout (what lives where)

- `src/main.tsx` + `src/App.tsx` — entrypoint and shell. `App.tsx` fetches the plan bundle (`GET /api/plans/:id` + `/budget` + `/actuals` + `/workforce` in parallel, decoded at the boundary) with a **demo fallback** (`demo-entity.ts` + `demo-contables.ts` + `demo-workforce.ts`) when the backend is unreachable or a sibling fails its decoder; it keeps the viewer's `ops` and derives `livePlan = applyOps(basePlan, ops)` for the EVM panel. Online it also keeps the CR queue (`GET /api/plans/:id/change-requests`, refetch after propose/decision), passes `onProposeChangeRequest` down to the changeset zone and renders `ChangeRequestsPanel`; after an apply (or a decision 409) it bumps `reloadKey` so the bundle refetches and the viewer REMOUNTS via `key={planId:revision}` (its internal events state doesn't re-init from props alone — existing limitation). Offline: CRs/propose hidden, workforce falls back to the demo builder.
- `src/components/gantt-plan/` — app-level viewer (`GanttPlanViewer.tsx` is the **umeJSON black box**; optional `workforce` prop adds the «Cuadrilla» tree column), the changes JSON panel (`ChangesetPanel.tsx`, with the propose button when online), the CR queue (`ChangeRequestsPanel.tsx`, patrón `EvmPanel`: badges de estado, impacto congelado, Aprobar/Rechazar/Aplicar) and the EVM cards (`EvmPanel.tsx`). This is where to add app features.
- `src/components/reui/gantt/` — **vendored gantt engine** (NOT an npm dep). Edit `gantt.tsx` (main) and siblings here when extending the engine. New generic props for the tree panel live around `gantt.tsx:1215`.
- `src/components/reui/gantt/gantt-color.ts` — concrete-color helpers for the bar paint model. **All phase colors must be concrete hexes**; `var()` chains fail silently in some browsers (the whole chain goes invalid and paints transparent). Exports `baselineTones(color, stack)` for baseline marks (pastel ramp by depth) and `barTones(color)` for live bars (80% pastel + phase at α 0.85). Also `DIRTY_TINT = "#fecaca"` (red-200) for the modified/drifted state — gray-200 was retired: it sat at the same OKLCH lightness as every resting pastel (L≈93, chroma ≈0) and was invisible next to them.
- `src/components/ui/` — shadcn-style primitives. `slider.tsx` is **custom** (no native `<input type="range">`); it has its own pointer/keyboard handlers.
- `src/data/plan-departamento.ts` — synthetic plan regenerated on every mount, anchored to the current week (see `:57`). WBS schema v2. Phase `color` is a concrete hex (Tailwind 500-level) so every paint path (live bars, baseline tones, swatches) renders without runtime CSS-variable resolution. A few events ship with seeded `baselines` so the bitácora has content on load (panel + «Líneas base» toggle); they keep that history untouched. Re-exports types from `@/lib/plan-types` for compat.
- `src/lib/plan-types.ts` — shared types: `PlanJSON`, `PlanEvent` (+`baselines?`), `PlanBaseline`, `PlanResource` (+`responsable?`), `PlanPhase`, `EventData` (+`initialStart?`/`initialEnd?`, +`baselines?`). `data/` imports types from here, never the other way. The bitácora de líneas base lives in `EventData.baselines` (append-only snapshots; only real captures populate it — see `plan-mapper.ts`); `initialStart/End` are the hidden "modified vs original" anchor — not visible as a bitácora entry until the first capture on a drifted bare task materializes them as LB1.
- `src/lib/plan-mapper.ts` — `PlanJSON` → `GanttEvent[] + GanttResource[]`. Pure on the plan received: phase colors come from `plan.phases`, status is derived from the event's own `progress`, `responsable` comes from `resource.responsable`. Recursive tree builder, preserves sibling order, treats orphans/cycles as roots. **No synthetic LB1**: baselines exist only where a real capture happened (the seeded demo history, or an explicit *Fijar línea base*); events without history carry none. A load-time LB1 used to anchor every bar's original dates, so each drag left a full-size colored remnant pinned at the old spot — removed. Instead the mapper stamps `initialStart/initialEnd` into `EventData` so drift on a bare task measures against the plan's original dates without polluting the bitácora. First explicit capture on a *drifted* bare task materializes LB1 from those initial dates and appends the capture as LB2; a clean bar captures nothing (see *Fijar línea base en cascada* below).
- `src/lib/umejson/schedule.ts` — pure dependency graph helpers. **`dependentClosure(deps, seedIds)`** returns the transitive successors reachable from `seedIds` along `fromEventId → toEventId` (BFS, visited set, seeds excluded). Used by *Fijar línea base* to fan out captures across dirty dependents. **`wouldCreateCycle`** is the edit-time veto on `from → to`. **`cascadeSchedule`** is the forward-only forward pass that emits per-edge documented adjustments (see `ChangesetPanel` for the codec surface).
- `src/lib/umejson/baselines.ts` — **política de drift promovida** (runtime-pura): `vigenteBaseline` (máxima versión, no última posición), `driftReference`/`isDrifted` sobre tipos del plan (ISO strings; se comparan **instantes**, no strings — `…Z` y `…T00:00:00.000Z` son el mismo momento), `driftDays` (mismo redondeo que el panel de bitácora) y `restoreBaselineOp` (reversión a una versión capturada como `UpdateOp` — la bitácora es read-only, restaurar ES una edición). El viewer adapta `GanttEvent`→`DriftSubject` en su único punto de traducción (`isDriftedEvent`); no existe otra copia de la regla.
- `src/lib/umejson/change-request.ts` — contrato del módulo de control de cambios (runtime-puro): entidad propia **`GanttChangeRequest`** (el schema del plan queda congelado en v2), `ChangeRequestPayload` anclado al plan (`planEntityId` + `planAnchor` + **`planRevision`** — el binding que protege de verdad: `planAnchor` es una fecha que `applyOps` preserva intacto, así que ediciones intermedias se le escapan; la revisión no — apply contra otra revisión es 409 y la CR hay que re-proponerla), `buildImpactSnapshot(basePlan, ops, budget?)` (afectados = ops + `dependentClosure` sobre el grafo post-ops; Δ congelado al proponer contra vigente baseline ?? fechas del plan base; eventos creados no llevan referencia; con budget adjunta **`costImpact`** — modelo labor-burn: `dailyLaborBurn = breakdown.labor / duraciónDíasReferencia`, `projectedExtraCost = Σ driftDays × burn` con signo [negativo = ahorro], `extendedDays = Σ driftDays > 0`; sin budget no hay costImpact, sin desglose el burn es 0), `createChangeRequest` (el snapshot nace del MISMO plan al que se ancla), `buildChangeRequestEntity` (envelope nuevo, `crypto.randomUUID()`, relation → plan), transiciones legales `proposed → approved | rejected`, `approved → applied` (terminal; `transitionChangeRequest` devuelve null en ilegales), y `encodeChangeRequest`/`decodeChangeRequest` con la misma disciplina sentinel/statusLog que `encodeUpdatedPlan`. El `statusLog` del payload acepta timestamps SENTINEL (propuesta pre-persist); el `lifecycle` del envelope no. Actores (`requestedBy`/`decidedBy`) reservados vía SENTINEL hasta que el backend provea identidad (hoy: `DEFAULT_ACTOR`).
- **Fijar línea base en cascada** (`GanttPlanViewer.captureBaseline`): only bars that are *drifted* (their live dates differ from their drift reference — vigente baseline, else the mapper-stamped original dates; see `driftReference` in `umejson/baselines.ts`) capture. The seed follows the same rule as its transitive dependents along the dependency graph: a clean bar gets no entry, because snapshotting an unmoved bar would append an entry identical to its reference — a duplicate whose only effect was a ghost twin painted under the live bar. **First capture on a drifted bare task materializes LB1 lazily**: version 1 at `initialStart/initialEnd` with `capturedAt = plan.anchor` and reason `baselineOriginalReason` ("Carga inicial del plan"), then the capture as LB2 — the two-entry log the old load-time LB1 used to give, without painting ghosts on unmoved bars. Seed reason `baselineManualReason`; drifted dependents capture with reason `baselineCascadeReason(seedTitle)`. All capture entries share a single `capturedAt`. Persisted state only: «Reiniciar plan» wipes everything as before; ChangeOps are not touched.
- **Baseline ghosts are opt-in.** `getEventBaselines` (viewer) returns marks ONLY while the «Líneas base» toggle (`showAllBaselines`) is on; by default the timeline paints no baseline marks at all. The newest bitácora entry is the drift REFERENCE — its presence is signaled by the dirty tint, never by an ambient ghost: painting it by default stamped a twin under the live bar at capture time that only "revealed" itself after the bar moved. With the toggle on, the full bitácora fans out (newest = full-size stack 0, older = 3px lines). The bitácora panel and the hover-time reprojection (`eventBarOverlays`) read `data.baselines` directly and work regardless of the toggle.
- `src/lib/umejson/schema.ts` — `UmeJsonEntity` type + `decodeUmePlan()` hand-rolled validator (envelope + payload). Exports `SENTINEL = "RESERVED_FOR_SYSTEM"`, `ENTITY_NAME = "GanttPlan"` and `validateUmeEnvelope()` (shared envelope checks for the sibling entity decoders).
- `src/lib/umejson/cpm.ts` — **CPM runtime-puro**: `cpmSchedule(plan)` computa forward pass (ES/EF, reusando `earliestStart` + orden Kahn de `schedule.ts`), backward pass (LS/LF desde el fin del proyecto = max EF), holgura total (LS−ES, días corridos, mismo redondeo que la bitácora) y conjunto crítico (float 0). Convención **as-planned**: ES = max(inicio planificado, restricciones) — la holgura que el planificador "guardó" arrancando tarde NO es float. Una tarea aislada es su propia ruta crítica. El viewer señaliza barras críticas con un **trazo `inset-ring` en el color de fase** vía `getEventBarClassName` (hook genérico del motor); NUNCA con el relleno — el invariante bitono es **reposo siempre claro (pastel de fase o `DIRTY_TINT`), full-strength reservado al overlay de avance**, para que una crítica al 0% no se lea como avance.
- `src/lib/umejson/budget.ts` — entidad hermana **`GanttBudget`** (BAC por evento, moneda, time-phasing `uniform`, `relations[] → plan`): tipos, `buildBudgetEntity` y `decodeBudget(input, plan?, planEntityId?)` con el mismo DSL de schema (BAC ≥ 0 finito, refs contra el plan suministrado, relación exactamente 1 → GanttPlan). El payload v1 ganó **`breakdownByEvent?`**: partición `labor/material/equipment` por evento que debe sumar EXACTO al `bacByEvent[eventId]` (igualdad exacta, partes ≥ 0 finitas); opcional/aditivo, `schemaVersion` sigue en 1.
- `src/lib/umejson/workforce.ts` — entidad hermana **`GanttWorkforce`** v1 (RRHH de obra): `crews: [{ id, title, specialty, headcount, dayRate }]` + `assignmentByEvent: Record<eventId, { crewId, headcount }>]`, `relations[0] → GanttPlan` (exactamente 1). Decoder con `validateUmeEnvelope` + refs cruzadas (crew inexistente, evento desconocido vs plan, headcount ≥ 1, dayRate ≥ 0 finito) + `buildWorkforceEntity`.
- `src/lib/umejson/actuals.ts` — entidad hermana **`GanttActuals`** (AC acumulado por evento + `dataDate` de corte + `planAnchor`): `decodeActuals` valida el corte ISO, AC ≥ 0, refs contra el plan y el cross-check de `baselineVersionByEvent` contra la bitácora real (la versión anclada debe existir).
- `src/lib/umejson/evm.ts` — **EVM runtime-pura**: `computeEvm(plan, budget, actuals)` produce PV (time-phasing uniforme del BAC sobre la ventana de referencia de drift — baseline vigente/anclada, si no las fechas del evento, clamped [0, BAC]), EV (BAC × progress), AC (corte) y SV/CV/SPI/CPI/EAC/ETC/TCPI/VAC por evento y proyecto. Índices null cuando el denominador carece de sentido (PV 0, AC 0, CPI 0 → EAC); CPI 0 con AC > 0 es una respuesta real, no null. Nada se persiste — EVM es una lente. `pvFraction` exportada para tests.
- `src/data/demo-entity.ts` — `buildDemoEntity()` + `DEMO_PLAN_ID`: el envelope demo compartido por el fallback de App y el seed del backend (una sola definición).
- `src/data/demo-contables.ts` — builders demo de `GanttBudget`/`GanttActuals` sobre un plan dado (tarifa por fase × días para BAC, con desglose labor/material/equipo que suma EXACTO al BAC — labor 45–60% según fase, enteros, equipo absorbe el redondeo; BAC × avance × wiggle determinista [0.85–1.15] para AC; ancla de baseline vigente donde hay bitácora). Mismo patrón que las baselines sembradas: sintético pero realista.
- `src/data/demo-workforce.ts` — builder demo de `GanttWorkforce`: las ~14 cuadrillas derivan de `RESPONSABLES` (única fuente: `plan-departamento.ts`), cada una con especialidad y tarifa/día/persona realista (peón ≈ 850, albañil ≈ 950, eléctrico ≈ 1 100, residencia ≈ 1 500 MXN); `assignmentByEvent` = evento → cuadrilla del `responsable` de su recurso (demo 1:1). Determinista (hashes sobre ids).
- `server/` — **gantt-api** (paquete del workspace): Fastify + pg escuchando SOLO en `127.0.0.1:4600` (nginx proxyea `/api/` mismo origen). `src/db/migrations/*.sql` + runner idempotente (`migrate.ts`); `entities.ts` (store híbrido: documento íntegro en JSONB + columnas promovidas `status`/`revision`/`plan_entity_id` mantenidas por el servidor, lock optimista vía `revision`; `PutEntityArgs.status` overridea la columna promovida para CRs — `payload.status`, no `state.current`, que el índice `ume_cr_queue` filtra por `status='proposed'`; `stampChangeRequestSentinels` además del envelope estampa el `statusLog` del payload CR y los actores; `seedOverwrite` = refresh incondicional de hermanas demo); `index.ts` (health + GET/PUT `/api/plans/:id` y `/api/plans/:planId/budget|actuals|workforce` vía `registerEntity`; endpoints CR propios — NO via `registerEntity`, semántica distinta: `GET /api/plans/:planId/change-requests?status=` cola `created_at DESC`, `POST` propone con `createChangeRequest` contra el plan almacenado + `buildChangeRequestEntity` + decode defensivo del borde (ops con targets inexistentes → 422) + persist con `status: "proposed"`, `POST /api/change-requests/:id/decision` — `transitionChangeRequest` null → 422, y `to=applied` verifica `cr.planRevision === planRow.revision` (mismatch → 409 `{ currentRevision }`, la CR queda approved) y en UNA transacción escribe plan (`applyOps`, `statusLog` append `«CR aplicada: <id>»`, revisión +1) + CR `applied`; `DEFAULT_ACTOR` de `server/.env` estampa `requestedBy`/`decidedBy`). ## Bar paint model (bitono)

Live bars are painted in two layers; both tones come from the consumer through `GanttViewConfig`:

- **Resting surface** (`--gantt-bar-tint`): soft pastel, concrete hex. Defaults to `var(--gantt-event-color) / 20` (translucent) when no tone is supplied; switches to opaque (`data-bar-tinted` attribute, driven by `colorOverride` OR `progressTintOverride`) when any tone is provided. Hover/selected darken via `bg-black/5` on the opaque layer.
- **Progress overlay** (`--gantt-progress-tint`): full-strength phase color at α 0.85. Border at α 0.65. Defaults to `var(--gantt-event-color)`; switched by `progressTintOverride`. The two layers can move independently — a consumer paints a bitono.

Consumer entry points on `GanttViewConfig`:

- `getEventBarTone({ event }) => { resting?, progress? } | undefined` — per-event bitono. The `GanttPlanViewer` uses this to derive the resting fill from `barTones(ev.color)` and to mark the bar DIRTY (resting = `DIRTY_TINT`, red-200) when `ev.start/end` differ from its drift reference (vigente baseline = highest-version `data.baselines` entry, else the mapper-stamped `initialStart/initialEnd`). Drag-release and *Fijar línea base* both flow through `events`, so the dirty bit updates without an effect. Callback identity MUST be stable (wrap in `useCallback` over the derived `Map<eventId, tone>`).
- `getEventBarClassName({ event }) => string | undefined` — per-event extra classes on the live bar (merged after the engine's own). The channel for STATE chrome that must not borrow the fills (the critical-path `inset-ring-1 inset-ring-(--gantt-event-color)` stroke). Same memoize contract as `getEventBarTone`.
- `getSummaryBarTone({ resource, events }) => { resting?, progress? } | undefined` — same contract for parent rollups. Used so the inline summary bar matches the live-bar bitono.
- `eventBarOverlays[eventId].progressColor?: string` — companion to `color` for history-version previews: `color = baselineTones(...).fill` (pastel), `progressColor = baselineTones(...).full` (strong), so hovering a bitácora entry shows the version's bitono on the bar itself.

Vendored engine additions: `GanttBar` exposes `progressTintOverride`; both overrides feed CSS vars and turn on `data-bar-tinted` so the resting fill switches to opaque.

## Conventions (differ from defaults)

- **Styling**: Tailwind v4 with `@theme inline` and `data-[slot=…]` / `data-[state=…]` variants. No CSS modules.
- **Types**: `any` is forbidden unless marked with an explicit eslint-disable and a comment explaining the adapter.
- **Comments**: only where intent isn't obvious.
- **WBS depth is color, not indent.** Titles are left-aligned at the gutter; depth shows as row background via `wbsLevelStyle(depth)`. The depth slider (`WbsLevelSlider` in `gantt-plan/`) controls `collapsedGroups`: groups with `depth >= level` collapse. Default level = `maxDepth` (all expanded).
- **Concrete-hex colors only.** Phase colors flow through `barTones()` and `baselineTones()` → CSS background, and the derivation chain uses `canvas.getContext("2d").fillStyle` for runtime resolution. CSS variables in `var()` chains are tolerated by the helpers but unreliable in the wild; pin hexes in `data/plan-departamento.ts` to keep paint predictable.
- **PlanJSON v2 quirks** (`plan-departamento.ts`):
  - `parentId` is free — can point to any resource, not just a phase.
  - `phaseId` is **inheritable**: missing `phaseId` falls back to the nearest ancestor's (bar color comes from the resolved chain).
  - `PlanPhase` is only color metadata (`id`, `title`, `color`) — no `resourceIds`.

## Verification order

Run after changes:

```
pnpm lint && pnpm build && pnpm verify
```

(`tsc -b` runs inside `build`, so type errors surface there. Lint is fast; run first. `pnpm verify` round-trips the umeJSON codec via `node --experimental-strip-types`.)

Backend changes add:

```
pnpm --filter server typecheck && pnpm --filter server migrate
curl -s localhost:4600/api/health   # smoke (db must be true)
```

## Deploy

`https://gantt.aeon-ia.com/` is the live demo for this project. **Every change set ships to it** — verification passing is not enough, the user is on this subdomain. Treat the next command as a fourth step of the workflow above; do NOT finish a task without running it.

```
pnpm build && rsync -a --delete dist/ /var/www/apps/gantt/
```

- `pnpm build` regenerates `dist/` with a new content-hashed bundle name; the rsync below only overwrites what exists.
- `--delete` is mandatory — stale hashed assets linger otherwise and nginx happily serves them.
- After the rsync, confirm the deployment took: `curl -s https://gantt.aeon-ia.com/ | grep -oE 'assets/index-[A-Za-z0-9_-]+\.js'` should match the hash printed by `pnpm build`. If it doesn't, the rsync didn't land.
- If the user reports "no veo cambios", they are almost certainly hitting a cached `index.html` (assets are hash-busted and update on their own). Suggest a hard reload (Ctrl+Shift+R / Cmd+Shift+R) and re-check the served bundle hash against `ls dist/assets/`. The vhost pins `location = /index.html { add_header Cache-Control "no-cache"; }` so the document always revalidates (ETag 304s) while hash-busted assets stay cacheable — do NOT remove that header: without it heuristic caching serves a stale document referencing an old bundle after a deploy.
- **Backend**: the API runs as the systemd unit `gantt-api.service` (user `gantt`, `EnvironmentFile=server/.env`, `ExecStart=node server/src/index.ts`). Code changes need `systemctl restart gantt-api.service`; nginx proxies `/api/` → `127.0.0.1:4600` from the TLS vhost (same origin, no CORS) with `limit_req` 10r/s burst 20 (zone `gantt_api` defined in `/etc/nginx/conf.d/gantt-api-limit.conf`). Credentials live ONLY in `server/.env` (gitignored, mode 640 root:gantt) — never in tracked files.

## Gotchas

- The gantt engine is **vendored**, not installed from npm. There's no `@reui/gantt` in `package.json` — don't add it; extend `src/components/reui/gantt/` directly.
- The repo is a **pnpm workspace** (`pnpm-workspace.yaml` → `server`); install at the root installs both packages.
- `src/lib/umejson/` is **runtime-pure**: no value imports with the `@/` alias (the path alias is resolved by Vite/tsc, not by Node). Imports between modules in that tree use relative paths with explicit `.ts` extensions (`from "./schema.ts"`) so the same files can be loaded by `pnpm verify` under `node --experimental-strip-types` AND by `tsc -b`/`vite build` AND by `server/src/index.ts` (Node ≥ 22.18 strip-types, no transpiler).
- `server/tsconfig.json` uses `moduleResolution: bundler` (typecheck-only, noEmit) so the frontend tree's `@/` alias imports resolve; at runtime only `.ts`-suffixed relative imports are ever executed.
- `tsconfig.app.json` has `noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly`, `verbatimModuleSyntax: true`. Watch for unused imports and enum-style code.
- README's "Scripts" section says `npm install` — **the lockfile says pnpm**. Use pnpm.
